---
name: Stale VPN host route breaks reachability monitoring
description: A leftover, more-specific kernel route to a client's VPN IP on an old tun device can silently override the live session's subnet route.
---

On the NetPulse production OpenVPN server, `ip route` can show a stale host route to a router's VPN address (e.g. `10.8.0.2 dev tun0 ... src 10.8.0.1`) alongside the correct, live subnet route on a different tun device (e.g. `10.8.0.0/24 dev tun1 ... src 10.8.0.1`) from the current `openvpn-server@netpulse` session (confirmed via `sudo cat /run/openvpn-server/status-netpulse.log`, which lists only one live client).

**Why:** Linux routing uses longest-prefix match, so the leftover host route on the stale tun device wins for any traffic the server sends to that exact IP, even though the client's real, live session is on a different tun device. This breaks more than ping-based monitoring — it silently breaks RADIUS Access-Accept/Reject replies too, since FreeRADIUS answers to the router's VPN address the same way, so PPPoE/Hotspot customers on that router can't authenticate even though the tunnel itself is healthy. It does not affect traffic that never targets the VPN-private address (e.g. the provisioning callback, which calls the router's public serverUrl, not the VPN IP).

**Confirmed root cause on this host (2026-08-26):** the "stale" tun device was not an orphaned/dead process — it was a second, fully live systemd unit, Ubuntu/Debian's default template `openvpn@server.service` (reading `/etc/openvpn/server.conf`, distinct from the dedicated `openvpn-server@netpulse.service` reading `netpulse.conf`), running since boot. It happened to hand its own client the same `10.8.0.0/24` address range as NetPulse's VPN, causing a real IP collision, not just a leftover route. The operator confirmed it was cruft from an earlier, abandoned setup attempt and it was disabled: `sudo systemctl disable --now openvpn@server`. After that, `ip route | grep <subnet>` showed only the correct `openvpn-server@netpulse` route and RADIUS reachability was restored immediately, with no VPN subnet change or router reprovisioning needed.

**How to apply:** Before assuming an OpenVPN data-path or cipher problem, run `ip route | grep <vpn-subnet>` and cross-check against `sudo cat /run/openvpn-server/status-netpulse.log` for the actually-live session's device. Then run `systemctl list-units --type=service --all | grep -i openvpn` — a second *running* OpenVPN unit (not just a dead process) is the more likely cause than a truly orphaned route. Per the dedicated-RouterOS-VPN-boundary rule, never disable or reconfigure a non-NetPulse-looking unit without the operator explicitly confirming it isn't a separate business-critical VPN; once confirmed, disabling the extra unit is the fix — no need to change NetPulse's own VPN subnet or reprovision routers.
